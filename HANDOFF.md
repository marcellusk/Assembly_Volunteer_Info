# HANDOFF — Assembly Info Builder

Read this first if you are a developer or an AI assistant picking up this project.
It explains what the project is, how the code works, and the non-obvious decisions
and traps. See `JOURNAL.md` for the change history.

## What this is

A tool for organizing volunteer information at multi-day events (assemblies/
conventions, typically Friday–Sunday). Volunteer departments ("groups" — Parking,
Cleaning, Stage, Seating, …) each need rosters, schedules, contact lists, notes,
and maps distributed to non-technical volunteers on their phones.

Two artifacts, one codebase:

1. **`Assembly Info Builder.html`** — the whole project. A single self-contained
   HTML file (vanilla JS, zero dependencies, no build step, no server). An
   overseer opens it in a browser, edits event data in a friendly UI, and exports.
2. **Exported viewer files** (e.g. `Demo Regional Convention - Volunteer Info.html`)
   — generated by the builder. Also single self-contained HTML. View-only by
   design (the "builder + viewer-only exports" decision). Volunteers swipe
   left/right between groups, tap Fri/Sat/Sun tabs, tap phone numbers to call,
   tap images to zoom.

Everything (including images) is embedded, so files can be sent by text/email and
opened offline from a phone's Files app.

## Core constraints (do not break these)

- **Single file, no dependencies, no build step.** Users are non-technical; the
  deliverable must stay "open this file in a browser."
- **Exports are view-only.** Editing happens only in the builder.
- **Everything embedded** — no network requests at view time (files are opened
  from `file://` and offline).
- **Target browsers:** modern Chrome/Edge/Safari, desktop + mobile. The viewer is
  written in conservative ES5-ish style; the builder uses light ES5+ (arrow-free).

## File anatomy of `Assembly Info Builder.html`

Top to bottom:

1. `<style>` — builder CSS.
2. `<script type="application/json" id="project-data">` — **empty in the shipped
   builder**; populated when the user clicks "Save Project File" (see persistence).
3. Top bar (`✨ New Event`, `💾 Save Project File`, `📱 Export for Volunteers`)
   and `<div id="app">` (builder UI renders here).
4. `<script type="text/template" id="viewer-src">` — **the entire viewer page as
   inert text**. This is the template for exports.
5. Main `<script>` — builder logic: helpers, `seedProject()` (demo data with five
   embedded base64 map images), persistence, image compression, export, and DOM
   rendering (`render()` and per-section editors).

### The `</script>` escaping trick (important)

The viewer template lives inside a `<script type="text/template">` tag, so it must
not contain a literal `</script>` sequence anywhere (the HTML parser would close the
container early). All script closes inside the template are written as `<\/script>`.
At export time:

```js
tpl = tpl.split('<\\/script>').join('</scr' + 'ipt>');
```

If you edit the viewer template, never introduce a raw `</script`, including inside
JS strings within the template.

### The `$` replacement trap (already fixed — keep it fixed)

`String.prototype.replace` with a **string** replacement treats `$&`, `$'`, `` $` ``
specially. The project JSON or a title could contain those. All template
substitutions therefore use **function** replacements:

```js
.replace('__PROJECT_JSON__', function(){ return json; })
```

JSON embedded into any script tag also escapes `<` as `<` to prevent
`</script>` injection from user content.

## Data model

One JSON object (`project`) is the single source of truth:

```js
{
  projectId: "x8f3k2…",     // identity — guards the localStorage restore banner
  savedAt: 1753…,           // ms timestamp, updated on every persist
  event: {
    title, subtitle,
    footer,                  // shown at the bottom of every group panel (multiline)
    days: [ {id, label}, … ] // usually friday/saturday/sunday; fully editable
  },
  groups: [                  // one per department; viewer panel order = array order
    { id, name, hue,         // hue: oklch hue number (palette in HUES array)
      sections: [ … ] }
  ]
}
```

### Section types (the "flexible building blocks" decision)

Each group's page is composed of typed sections, added/reordered/removed freely:

| type | shape | per-day? | viewer rendering |
|---|---|---|---|
| `contacts` | `items: [{name, role, phone}]` | no | red-tinted highlight box, tap-to-call |
| `roster` | `perDay: {dayId: [{name, people: [{name, role}]}]}` | yes | card per named area (lot/zone/section) |
| `schedule` | `perDay: {dayId: [{time, name, phone}]}` | yes | time-slot rows, tap-to-call |
| `notes` | `byDay` flag; `text` (shared) or `perDayText: {dayId: str}` | optional | yellow note box; hidden when empty |
| `images` | `items: [{caption, src}]` (src = data URL) | no | 2-col grid (or full-width if single), tap-to-zoom lightbox |
| `directory` | `items: [{name, phone, assignment, constraints}]` | no | collapsible, search box, **alphabetized at render time** (source order irrelevant) |

Per-day sections key their data by `day.id`. Adding/removing a day in the event
editor adds/deletes those keys across all groups. Roster and schedule editors have
a "Copy <day> to all other days" helper (deep-clones via `clone()` =
`JSON.parse(JSON.stringify(...))` — the whole codebase uses this for cloning and
mutation is done directly on `project` followed by `persist()` + `render()`).

## Persistence model

- **Autosave:** every edit calls `persist()` → debounced (400 ms) write of the whole
  project to `localStorage` under key `assembly-info-builder`. Works on `file://`
  in Chrome/Edge.
- **Save Project File:** clones `document.documentElement`, writes the project JSON
  into the clone's `#project-data` tag, empties `#app`, downloads
  `"<title> - PROJECT (master).html"`. That file **is the builder** with data baked
  in — the durable, portable copy.
- **Load precedence** (in `loadProject()`): embedded `#project-data` wins; if
  localStorage has a **newer** save of the **same `projectId`**, a banner offers to
  restore it (never auto-applies, never offers across different projects). Fresh
  builder with no embedded data → localStorage → `seedProject()`.
- **New Event:** confirms, then replaces the in-browser project with `blankProject()`
  (empty groups, Fri/Sat/Sun). The user is warned to Save Project File first,
  because localStorage holds only one project at a time.

## Image pipeline

`compressImage(file, cb)`: FileReader → `<img>` → canvas, downscale to max 1600 px,
re-encode JPEG q0.85 on a white background; keeps the original data URL if it was
already smaller. This is the "auto-compress" decision — a full multi-group file
should stay in the low single-digit MB. Images are stored as data-URL strings in
section items and travel with the JSON everywhere.

## Name autocomplete (directory-fed)

`directoryPeople()` unions the items of every `directory` section in every group
(dedup by trimmed lowercase name, alphabetized) into a single shared
`<datalist id="people-list">` (attached to `<body>` so it survives `#app`
re-renders; refreshed in `render()` and on the `persist()` debounce).
`nameInput(obj, placeholder, flex, phoneInput?)` wraps `textInput` for name
fields: it attaches the datalist, and when given a sibling phone input it
auto-fills `obj.phone` on an exact (case-insensitive) directory match — **only
when the phone is empty**; a typed phone is never overwritten. Used by the
contacts, roster-people, schedule-row, and directory editors. Data stays inline/
denormalized — this is deliberately the lightweight half of the "people
registry" roadmap item; picking a name copies values, it does not create a
reference.

## Group share: per-group JSON export/import

Supports a **distributed data-entry workflow**: each department captain gets a copy
of the master builder file, fills in *their* group, and clicks **⇪ Export group
JSON** (group settings row). They send the resulting `.json` to the coordinator,
who clicks **📥 Import group JSON…** (Groups card) in the master copy. No serial
file passing; the coordinator never types other departments' data.

File format (`schemaVersion: 1`):

```json
{ "format": "assembly-info-group", "schemaVersion": 1, "exportedAt": "…",
  "event": { "title": "…", "days": [ {"id": "friday", "label": "Friday"}, … ] },
  "group": { "name": "…", "hue": 45, "sections": [ … ] } }
```

Rules and invariants:

- **Images never travel in group JSON** (owner decision; security concern). Export
  blanks every image `src`. On import, empty-src entries render as "missing —
  click to attach" placeholder buttons in the builder's images editor; the viewer
  filters out src-less images entirely (both grid and lightbox index use the same
  filter — keep them in sync).
- **`importGroupJson` → `sanitizeSection` is a security boundary.** Imported JSON
  is untrusted. Never bypass it: unknown section types are skipped; every field is
  copied through a whitelist with length caps (`cleanStr`); fully-empty rows are
  dropped (`hasContent`); image srcs must match `DATA_IMG_RE`
  (`^data:image/…;base64,…`) or they are stripped. The image-src check matters
  because the viewer concatenates `src` directly into an HTML attribute — an
  unvalidated `"… onerror=…"` string would be XSS in a file distributed to every
  volunteer.
- **Day mapping** (`buildDayMap`): exported day → master day by id, then by
  trimmed case-insensitive label, then positionally for leftovers. Data for days
  that still don't map is dropped and counted in the import summary.
- **Name collision**: importing a group whose name matches an existing group
  (case-insensitive) prompts replace-or-keep-both. All ids (group + sections) are
  regenerated on import.
- The import ends with a summary `alert` (sections imported, images to attach,
  bad images removed, sections skipped, day lists dropped) — keep it honest; it's
  the coordinator's only feedback.

## Export mechanics

`exportViewer()`: read `#viewer-src` textContent → un-escape `<\/script>` →
substitute `__TITLE__` and `__PROJECT_JSON__` (function replacements) → download
`"<event title> - Volunteer Info.html"`.

## WhatsApp contacts

Contacts, schedule rows, and directory entries each carry an optional `wa`
alongside `phone`. On site volunteers often use WhatsApp because plain calls get
ignored as spam, so the viewer shows a green **WhatsApp** pill beside the phone
number and either can be tapped.

- `wa` stores **what the editor typed** — a phone number in any formatting, or a
  pasted WhatsApp URL. `waLink(raw)` converts it to a URL at render time
  (10 digits get a `1` prefix, same US assumption as the `tel:` links).
- **`waLink()` is a security boundary**: the result goes straight into an
  `href`. Only `https://wa.me/…`, `https://api.whatsapp.com/…` and
  `https://chat.whatsapp.com/…`, or a plain phone number, are accepted;
  everything else returns `''` and nothing is rendered. Verified against
  `javascript:`, `http:` (non-TLS), and lookalikes like `wa.me.evil.com`,
  `evil.com/wa.me/`, `wa.me@evil.com`. Import runs the same check and reports
  removals as `badLinks`. **The viewer re-validates independently** (`waHref`)
  rather than trusting the exported JSON — keep both copies in sync.
- **Empty means "no WhatsApp"** — never synthesize a link from the phone number,
  because not everyone has an account and a wa.me link to a non-WhatsApp number
  is a dead end. The `=` button in the editor is how "same number" is expressed.
- `contactFields(obj, phoneFlex, waFlex)` builds the phone + WhatsApp + `=`
  trio so all three editors stay identical; `nameInput` fills both fields from
  the directory via autocomplete, never overwriting typed values.
- The pill uses a **generic speech-bubble SVG**, not the WhatsApp mark, so the
  repository carries no third-party logo.
- **Directory inheritance**: `resolveContactLinks()` (called from
  `buildStaticView`, so it covers both renderings) fills any contacts or
  schedule row that has no `wa` from that person's directory entry, matched on
  the trimmed case-insensitive name across all groups' directories. A value
  typed on the row always wins. It runs on the **export copy only** — stored
  data is never rewritten behind the editor's back, so adding WhatsApp to the
  directory later applies retroactively without touching existing rows. The
  editor surfaces this as a `from directory: …` placeholder (suppressed on
  directory rows, which are the source).

## Group colors (any color, guaranteed readable)

Groups store `color`: a plain `#rrggbb` string the user picks from 12 presets or
a native `<input type="color">`. Hex, not oklch, because these values also feed
the static no-JS view that must render on old phones.

- **Never render `color` directly.** Call `groupUi(g)` → `{bg, fg, accent}`.
  `bg` is the render-safe background, `fg` is contrast-checked label text,
  `accent` is a brightened variant for the dark header (day-tab underline).
- **`ensureReadable(bg)` is the guarantee.** Some vivid mid-tones (hot pink,
  mid greens) fail WCAG AA against *both* white and dark text, so when no text
  color reaches 4.5:1 the background itself is nudged darker/lighter until one
  does. `g.color` always keeps exactly what the user picked; only the rendered
  value shifts. Fuzzed over 10k random colors: zero failures. The 12 `PRESETS`
  are chosen to already clear the bar, so clicking a swatch renders exactly the
  color shown — keep it that way if you edit the palette.
- **Colors are resolved once, at export**, in `buildStaticView()`, which stamps
  `g.ui` onto the exported project copy. The viewer and the static markup both
  read `g.ui`, so the two renderings can't disagree and the viewer needs no
  color math of its own.
- **Import validates strictly** (`normHex`): the value lands in a `style`
  attribute, so anything that isn't `#rgb`/`#rrggbb` is rejected and replaced
  with a preset. Never relax this.
- **Legacy**: schemaVersion 1 files stored a `hue` number from a fixed palette;
  `migrate()` converts it via `LEGACY_HUES` on every load and deletes `hue`.
  `colorPicker(target, onCommit)` is written against any object with a `color`
  property, so subgroups can reuse it unchanged.
- The picker re-renders on `change`, not `input` — re-rendering mid-drag would
  tear down the color input and close the OS picker. `input` updates the model
  and the live preview chip only.

## The no-JS static fallback (do not remove)

iOS previews HTML attachments (Messages, Mail, Files) with QuickLook, which
does **not run JavaScript** — a JS-only page shows as a blank dark screen there.
Exports therefore contain BOTH renderings:

- `buildStaticView(project)` (builder helpers) emits a complete plain-HTML,
  light-background rendering of everything into `<div id="static-view">`
  (`__STATIC_VIEW__` token), with a banner telling the reader how to get the
  interactive version. Identical per-day lists collapse to one "Every day" block.
- A head script sets `html.js`; the app's fixed-height/overflow-hidden/dark
  layout CSS is gated on `html.js`, and `html.js #static-view{display:none}`
  hides the fallback instantly when JS runs.
- **Images exist once**: the static `<img id="simg-N">` tags hold the data URLs;
  the embedded JSON's image items carry `"#simg-N"` markers, resolved from the
  static DOM at viewer boot (which then removes `#static-view` entirely).
  If you change either side, keep marker production and resolution in sync.
- When testing, always run the viewer once with JavaScript disabled
  (`page.setJavaScriptEnabled(false)` in puppeteer) — that IS the iPhone
  attachment-preview experience.

## Navigation axes (swipe = days, tap = departments)

**One `.panel` per DAY of the current department**, not one per department.
Horizontal swipe therefore moves Friday → Saturday → Sunday, which is the axis
volunteers actually move along; departments are chosen from the pill bar, which
rebuilds the day pages and keeps the day you were on (`setGroup`).

This was changed after the project owner — who built the file — reported "losing"
swipe on Android: nothing was broken, swipe was simply bound to departments while
everyone expected days. It also fixes single-department files, where department
swiping had nothing to move to.

Consequences to keep in mind when editing the viewer:

- `renderSection(sec, gi, dayId)` takes the day **explicitly**; it must never
  read the global `curDay`, because sibling pages render other days.
- Sections that aren't per-day (contacts, images, directory) repeat on every day
  page. Viewer images therefore carry `loading="lazy" decoding="async"` so
  off-screen day pages don't decode the same maps again — important on older
  iPhones with large map sets.
- `uiState` (directory open/search) is keyed by **group**, so the directory
  stays open across that department's day pages.
- Panels carry `data-di` (day index). The scroll listener maps scroll position
  to a day and re-renders the header only.
- The static no-JS view is unaffected — it renders every day inline already.

## Viewer behavior (inside the template)

- Layout: `body` = fixed-height flex column; sticky dark header (event title, group
  **pill bar** — hidden when only one group — and **day tabs** — hidden when only
  one day); below it `#swiper`, a horizontal `scroll-snap-type: x mandatory` flex
  row with one full-width, independently vertically-scrolling `.panel` per group.
- Swipe/pill sync: a debounced (80 ms) scroll listener computes
  `round(scrollLeft / clientWidth)` → active pill; clicking a pill smooth-scrolls.
- Day state is **global** across groups (you're at the event on one day).
- Re-renders preserve each panel's `scrollTop` and the swiper's `scrollLeft`.
- Phone → `tel:+1<digits>` links (US-centric; see roadmap).
- All user text goes through `esc()`; the only raw HTML injection is image `src`
  data URLs.

## User documentation

`README-HowTo.html` is the end-user guide (plain language, for non-technical
coordinators), with screenshots embedded as base64 so it's a single double-click
file like everything else. The raw PNGs are in `docs/screenshots/`. **When the UI
changes, the screenshots go stale** — regenerate them by driving a headless
Chrome (puppeteer-core, executablePath to the installed browser, `--no-sandbox
--allow-file-access-from-files`, clear localStorage so the demo seed loads) over
the builder at ~980px and the demo viewer at phone size (390×780), screenshotting
with page-absolute clip coordinates (`getBoundingClientRect() + scrollX/scrollY`
— viewport-relative clips capture the wrong region). Then re-embed each PNG into
the guide as a `data:image/png;base64,` URL. Keep the guide's language simple:
short sentences, no jargon, explain both *what to press* and *why*.

## How to test a change

No test framework; test in a browser:

1. Open `Assembly Info Builder.html`. Check the console is clean and the demo data
   renders. Edit fields, add/remove/reorder sections and groups, switch days.
2. Click **Export for Volunteers**; open the downloaded file. Verify: pill bar +
   swipe between all groups, day tabs change rosters/schedules/notes (Saturday
   Parking has an extra person; Stage notes differ per day), directory search and
   alphabetizing, tap-to-call `tel:` hrefs, image lightbox open/close.
3. Click **Save Project File**; open the downloaded master; verify data round-trips.
3a. Click **⇪ Export group JSON** on a group; re-import the file via **📥 Import
   group JSON…**; verify the replace/keep-both prompt, the import summary, and
   that image entries came back as clickable "missing" placeholders.
4. Reload the builder (localStorage restore), and test **New Event**.
5. Attach a large photo to an images section; confirm it is downscaled (export size
   stays reasonable).

## Known limitations / roadmap ideas

- One project per browser localStorage slot (master files are the real storage).
- `tel:` links hardcode the `+1` country code.
- No print stylesheet; no undo (deletes have `confirm()` prompts only).
- Directory is per-group; there is no cross-group person search.
- Builder text inputs commit on `input` without re-render; structural changes
  re-render fully — fine at current data sizes.
- Possible next steps: a "duplicate group" button, drag-to-reorder, optional PIN on
  exports, iCal export for schedules, print/PDF layout.
